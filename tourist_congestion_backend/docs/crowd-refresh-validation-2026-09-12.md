# 서울 혼잡도 재수집과 추천 반영 검증 (2026-09-12)

내부망 테스트 페이지에서 서울 혼잡도 관측이 모두 만료돼 추천에 보이지 않는 문제를 확인했다. 18:13:57 KST 기준, 연결된 12개 서울 영역의 최신 관측 시각은 모두 16:00으로 약 134분 전이었다. 현재 추천 엔진은 방문 시각이 현재에서 5분 이내이고 관측 시각이 0~30분 전일 때만 혼잡도를 사용한다. 그보다 오래된 값으로 현재 상태를 추정하지 않는다.

수집 전 로컬 SQLite를 `/private/tmp/feature-be-recommendation-core-before-crowd-refresh-20260912.sqlite3`에 백업하고 무결성 검사 `ok`를 확인했다. 대상 12개 영역은 `/private/tmp/feature-be-recommendation-core-crowd-refresh-20260912.json`에 남겼다. 공통 워커에 12개 작업을 등록해 일회성으로 실행했고 전부 성공했다. 각 영역의 최신 관측은 17:45로 갱신됐으며, 첫 검증 시각 18:14:50에는 약 29.8분 전이라 12개 모두 추천에 사용할 수 있었다. 공급자 원본을 호출한 시각을 관측 시각으로 바꿔 저장하지 않았다.

갱신 시각을 확인하려고 광화문·덕수궁 영역을 4회 더 조회했다. 이번 16개 작업은 모두 성공했고 서울 공급자 호출 예산 기록은 당일 25회에서 41회로 증가했다. 서울 관측 행은 27건에서 40건으로 늘었다. 같은 시각의 중복 관측은 새 행을 만들지 않고 갱신한다.

| 검증 요청 | 수집 전 | 재수집 직후 |
| --- | --- | --- |
| 서울시청, 반경 10km, 혼잡 선호 없음 | 상위 10개에 혼잡 근거 없음 | 상위 10개에 혼잡 근거 없음 |
| 서울시청, 반경 10km, 혼잡 선호 `normal` | 덕수궁 상위 10개 밖 | 덕수궁 6위, 관측 `normal`, 점수 기여 `distance`·`crowd`, 점수 98.78 |
| 덕수궁 좌표, 반경 10km, 혼잡 선호 `normal` | 유효한 혼잡 근거 없음 | 덕수궁 1위, 관측 `normal`, 점수 기여 `distance`·`crowd` |

실제 내부망 `POST /api/recommendations`에서도 덕수궁 좌표(37.565055, 126.976575), 반경 1km, `crowd_level=normal` 요청이 HTTP 200으로 반환됐고, 덕수궁 항목에 `crowd.level=normal`, 관측 시각 17:50, `score_contributors=['distance', 'crowd']`가 포함됐다. 임시 테스트 페이지에도 ‘덕수궁 · 혼잡도’ 예시 버튼을 추가해 같은 요청을 쉽게 만들 수 있게 했고, 영역별 최근 혼잡 단계와 신선·추천 사용 가능 건수를 구분해 표시한다.

## 신선도 한계

18:15:20에 같은 영역을 다시 조회했을 때 공급자 관측은 여전히 17:45로 30.3분 전이었고 추천에서 제외됐다. 18:17:05에도 17:45(32.1분 전)였으며, 18:19:07의 재조회에서 17:50(29.1분 전)으로 갱신됐다. **이번 관측에서는 새 값이 약 29분 늦게 도착했고, 현행 30분 만료 기준 안에 머무는 시간이 짧았다.** 이는 한 시간대의 실측이지 하루 전체 지연 분포나 운영 가용률은 아니다. 서울시의 [실시간 도시데이터 매뉴얼](https://data.seoul.go.kr/SeoulRtd/downloads/%EC%8B%A4%EC%8B%9C%EA%B0%84_%EB%8F%84%EC%8B%9C%EB%8D%B0%EC%9D%B4%ED%84%B0_%EB%A7%A4%EB%89%B4%EC%96%BC.pdf)은 통신사 인구 추정 예시에서 5분 단위 집계와 제공까지 약 15분의 가공 시간을 설명한다. 이번 API 응답의 실제 관측 나이는 그 예시보다 길었다.

이 때문에 일회성 재수집만으로 혼잡도 추천을 계속 사용할 수 있다고 볼 수 없다. 기본 요청은 원래 거리순이며, 혼잡 단계가 관측되더라도 사용자가 혼잡 선호를 요청하지 않으면 점수에는 넣지 않는다. 30분 만료 기준을 임의로 늘려 오래된 값을 현재 상태처럼 쓰지 않았다. 다음 검증에서는 수 시간 동안 주기적으로 원본 관측 시각과 조회 시각을 기록해 지연 분포와 유효 구간을 측정해야 한다. 그 결과를 보고 재조회 주기와 만료·점수 정책을 함께 정해야 한다. 현재 개발 서버에는 상주 수집 워커가 없으므로 자동 갱신도 보장되지 않는다.

이번 작업은 로컬 SQLite와 임시 테스트 페이지에서만 수행했다. 푸시·배포는 하지 않았다.
