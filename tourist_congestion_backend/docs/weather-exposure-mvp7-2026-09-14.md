# 날씨 노출 추천 mvp-7 — 2026-09-14 구현·고정 평가

## 현재 계약

추천의 `place.indoor_outdoor`는 기존 호환 라벨이고, `place.weather_exposure`는 **주된 방문 활동의 날씨 노출을 위한 별도 순위 정책**이다. `high / medium / low / unknown`은 실측 노출 비율이나 확률이 아닌 서열형 추정이다. 응답은 `level`, `activity`, `source`, `reason`, `conflict`, `conflict_reason`, `type_code`, `type_name`, `weight_factor`, `policy_version`, `persisted`를 제공한다. `unknown`이면 날씨 원점수는 `null`이며 좋은 날씨·안전한 날씨로 간주하지 않는다. 예보 자체가 결측·만료·부분적으로만 정상이어도 기존의 보수적 처리 규칙을 유지한다.

공식 TourAPI `lclsSystm3` 코드가 현재 장소 `subcategory`와 일치할 때만 유형 정책을 적용한다. 코드별 공식 명칭의 2026-09-14 선택 스냅샷은 [여기](./tourapi-type-codes-2026-09-14.json)에 보존했다. 코드 명칭은 공급자 분류이고 노출 `high / medium / low`는 **우리 정책**이다. `관광지` 같은 넓은 카테고리만으로 야외라고 하지 않는다. 새 체계 `lclsSystm3`가 없어도 구 `cat3`를 임의로 추측해 채우지 않는다. 매칭된 복수 출처 코드가 충돌하거나 저장 코드와 다르면 유보한다. 모호한 전시관, 수영장, 일반 공연장, 음식점 등은 유형만으로 노출을 확정하지 않는다. 유형 추정 `type_prior`의 점수 효과는 중립 50으로부터 `0.35`배에 한정한다. 날씨 근거 필수 필터와 실내 필수 필터에는 유형 추정만으로 통과시키지 않는다.

현재 수동 라벨은 최우선이고, 현재 설명·검증된 AI 근거가 있으면 주된 활동을 먼저 본다. 이름 추정과 공식 유형 추정이 서로 반대면 하나를 임의 선택하지 않고 `inference_conflict / unknown`으로 유보한다. 기존 검수 회수(`review_after_audit`) 장소는 새 유형 추정으로 되살리지 않는다. 수동 판정은 회수 기록보다 우선한다. 설명 해시가 달라지거나 개발용 placeholder이면 과거 자동 근거를 사용하지 않는다. `PlaceWeatherExposure`는 별도 버전·입력 해시·시각과 함께 오프라인 CLI로 저장한다. API 요청은 저장된 최신 프로필을 확인하거나 동일한 순수 함수로 계산할 뿐, Luna나 공공 공급자를 직접 호출하지 않는다. 2026-09-14에는 승인된 7곳만 CLI로 저장했으며 전국 45,716곳의 대량 저장은 하지 않았다.

기존 설명 규칙·수동 라벨의 `indoor/outdoor/mixed`를 날씨에 각각 `low/high/medium`으로 호환 매핑하는 경우가 있다. 그러나 요트·야영장처럼 실내 공간이 있어도 주활동이 날씨에 민감한 일부 **명시된** 유형은 높은 노출로 해석하되 효과를 최대 `0.35`로 제한한다. 실내외 선호 점수와 엄격 실내 필터는 이 별도 노출값 때문에 바뀌지 않는다. 공식 유형 추정과 설명·AI 근거의 방향이 다르면 `conflict`를 노출한다. 장소별 방문 목적·운영방식은 달라질 수 있어 이 정책은 안전 보증이 아니다.

Luna의 현재 요청 형식은 `gpt-5.6-luna`, Responses, strict structured output, `reasoning=none`, `store=false`이며 기존 6개 문맥 필드에 `weather_exposure`, `exposure_activity`, `exposure_reason`을 추가했다. 원문 인용·필드형·범위 검증 뒤의 AI 근거도 계수 최대 `0.5`, 엄격 실내 근거 불가다. **이번 변경에서 실 Luna 호출은 0회**이고 v4 날씨 필드는 mock 테스트만 거쳤다. 특히 v4는 indoor/outdoor 호환 라벨도 함께 유효해야 저장되므로, 호환 라벨이 `unknown`인 경우 AI가 날씨 노출만 판단한 제안은 아직 저장되지 않는다. AI의 독립 노출 판정이 실자료에서 작동한다고 주장하지 않는다. 오늘의 기존 일일 20회 한도를 우회하지 않았다.

## 데이터·재현·운영 범위

실제 동일 TourAPI 출처 `contentid=126508`의 경복궁은 장소명·주소·좌표 매칭 후 한 곳만 상세를 새로 조회해 개발용 placeholder 47자 설명을 공개 상세 1,261자로 교체했다. 전체 상세 재수집은 하지 않았다. SQLite `0008`, `0009` 마이그레이션 전 안전 백업은 `/private/tmp/weather-exposure-id1-backup.4ehuEV/`에 보존했다. 자동 삭제하지 않는다.

공식 코드 확인은 한국관광공사 `KorService2/lclsSystmCode2`의 상위 1·중분류 9·세분류 14·추가 1, 합계 **25개의 제한 요청**이었다. API 키와 원본 응답 전체는 문서·로그에 넣지 않았다. 공식 명칭을 추린 보존 스냅샷과 모델 정책은 다르다. 코드는 [weather_exposure.py](../places/services/weather_exposure.py)의 `TYPE_POLICY`, `TYPE_FAMILIES`, `WATER_ACTIVITY_CODES`를 수정해 확장하며 코드 근거/충돌 규칙과 고정 평가를 함께 갱신해야 한다.

로컬 프로필 CLI는 공급자 호출을 하지 않는다:

```bash
.venv/bin/python manage.py build_weather_exposure_profiles --limit 100
.venv/bin/python manage.py build_weather_exposure_profiles --place-id 1 --limit 1 --apply
```

첫 명령은 dry-run, 둘째는 한 장소의 수동 기록을 보호한 저장이다. 이번 승인 7곳 ID는 `1,3997,28656,2687,824,2346,883`; 결과는 high 4 / medium 1 / low 1 / unknown 1, 충돌 1이며 824는 검수 회수 상태를 그대로 보존했다. `--limit` 상한은 500이다. 추가 전국 apply나 AI 호출은 이 작업에서 하지 않았다. DEBUG 전용 `/test/backend/`에는 이 7곳의 현재 노출·출처와 실제/가상 날씨 비교가 표시된다.
