# 전국 수집 및 로컬 운영 검증 (2026-09-12)

검증 결과의 제품 판단과 우선순위는 [백엔드 실용성 보고서](../../BACKEND_PRACTICALITY_REPORT.md)에 별도로 정리했다.

이 기록은 로컬 SQLite와 실제 공급자 키로 수행한 검증이다. 공개 서버 배포, 푸시, 운영 DB 선정은 수행하지 않았다. 키 값과 키가 포함된 요청 URL은 기록하지 않았다.

## 수집 결과

| 항목 | 관측값 |

| TourAPI `areaBasedSyncList2` 보고 전체 | 68,993건 |
| 요청 크기 1,000건으로 완료한 페이지 | 69페이지 |
| 추천 대상 6개 카테고리 출처 | 62,782건 |

첫 전체 동기화는 약 109초 걸렸다. 공급자가 마지막 페이지의 `numOfRows`를 요청 크기 1,000이 아닌 실제 반환 건수 993으로 보내, 기존 코드가 빈 70번째 페이지를 한 번 더 호출했다. 요청 크기를 기준으로 종료하도록 고친 뒤 전체를 다시 동기화해 69페이지, 처리 대상 62,782건으로 끝났고 장소·출처 수가 늘지 않았다. `PRAGMA integrity_check`도 정상이다.

기존에 저장되지 않은 서울 카탈로그 9개 영역이 호출 없이 성공 처리되는 문제를 발견해 고쳤다. 이 9개 작업을 다시 실행해 모두 관측을 저장했다. 실제 워커는 예보 18건, 서울 영역 12건, 상세 20건, 전국 목록 2건을 성공 처리했고 대기·실패 작업은 없다. 새 실내외 분류 명령은 재실행 시 추가 변경 0건이었다.

수집 전 DB 백업은 `/private/tmp/feature-be-recommendation-core-before-full-sync-20260912-154121.sqlite3`, 전국 수집 후 백업은 `/private/tmp/feature-be-recommendation-core-after-full-sync-20260912-155846.sqlite3`이다. 두 번째 백업은 무결성과 주요 테이블 행 수를 확인했고, 백업 DB를 읽기 전용으로 연결해 추천 10건을 다시 계산했다. 실제 키의 문자열이 SQLite 파일에 포함되지 않은 것도 확인했다.

## 추천·운영 동작

- 7개 도시 중심부에서 반경 10km 후보가 각각 528~5,655곳이었고 모두 최대 10개를 반환했다. 기본 요청의 상위 10개는 7개 도시 모두 날씨 점수가 없었으며 평균 데이터 활용 비중이 0.30이었다. 기본 요청에는 카테고리·실내외 선호도 없으므로 대부분 직선거리에 의해 정렬된다.
- `문화시설` 선호와 `indoor` 필수 필터를 주면 서울은 162개 후보 중 10개(예보 10개), 부산은 28개 후보 중 10개(예보 8개), 제주는 7개 후보 중 7개(예보 5개)를 반환했다. 부족한 후보를 채우려고 필터나 반경을 완화하지 않았다.
- 같은 격자의 예보 조회를 요청 안에서 공유하고 실내외 미확인 장소의 불필요한 예보 조회를 생략했다. 서울 중심부 계산은 로컬에서 약 1.17초에서 0.14초로 줄었다. 이는 같은 컴퓨터의 단일 요청 측정값으로, 서버 부하 성능을 보장하지 않는다.
- `DEBUG=false` 로컬 HTTP 서버에서 `/healthz`는 200, 정상 추천은 200·10개, `limit=11`은 400이었다. 실제 HTTP 추천 한 건은 약 0.02초였다. 새 격자에 대한 동시 요청 5건은 모두 200(약 0.23~0.25초)이었고 보충 예보 작업은 하나만 등록됐다. 두 번째 워커 실행은 파일 잠금으로 거부됐다.
- Django 자동 테스트 77개, 마이그레이션 변경 검사, DB 무결성 검사를 최종 확인한다. `check --deploy`에는 기본 개발 비밀키, HTTPS 전환, HSTS, 보안 세션·CSRF 쿠키에 대한 경고 5개가 남는다.

## 실용성 판단과 남은 조건

전국 장소 목록의 수집·재수집·추천 응답은 기술적으로 동작한다. 그러나 현재 상태를 **전국에서 날씨·혼잡도를 충분히 반영하는 실용적인 추천 서비스**로 보기는 어렵다. 상세가 없는 장소는 45,686곳, 실내외 미확인은 43,878곳이며 혼잡도는 명시적으로 매핑된 서울 장소 2곳에만 적용된다. 날씨 점수는 실내외 근거와 해당 격자의 예보가 모두 있어야 붙는다.

모든 활성 장소의 상세를 조회하면 최대 약 91,372회(장소당 2회)의 TourAPI 호출이 필요하다. 현재 20곳/일 예약만으로는 약 2,284일이며, [개발계정 일 1,000회](https://www.data.go.kr/data/15101578/openapi.do)와 정기 작업 70% 예산을 모두 상세에 써도 약 131일이다. 따라서 전국 상세 일괄 완성 대신 요청·지역·품질 기준에 따라 우선순위를 정해야 한다. 기상청 3,632개 격자를 하루 8개 발표본마다 모두 수집하면 약 29,056회/일로 [개발계정 일 10,000회](https://www.data.go.kr/tcs/dss/selectApiDataDetailView.do?publicDataPk=15084084)를 넘으므로, 수요 기반 격자 수집이 필요하다.

출시 전에는 검증된 분류 근거 확대, 인기·요청 장소 중심 상세 수집, 사용자 요구에 맞는 기본 추천 정책, 서울 매핑의 실제 적용 범위, 운영 DB·서버와 비밀키/HTTPS 설정을 결정해야 한다. 이번 검증은 로컬 개발 서버와 SQLite에서 수행했으며 실제 운영 환경의 부하·복구·보안 검증을 대체하지 않는다.
