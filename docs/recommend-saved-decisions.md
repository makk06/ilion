# 추천·저장 탭 결정 요청

> 상태: **결정 대기.** 아래 항목이 정해지면 이 문서를 `DECISIONS.md`로 옮깁니다.
> 담당: 프런트엔드 — 추천 탭 / 저장 탭
> 관련 브랜치: `feature/recommend-saved-tab` (커밋 `e7bc0ea`)
> 구현 내용: [frontend-recommend-saved.md](./frontend-recommend-saved.md)

추천 탭과 저장 탭을 동작하는 수준까지 붙였습니다. 그 과정에서 혼자 정할 수 없거나,
임의로 정해 두고 팀 확인이 필요한 것들을 급한 순서로 정리했습니다.
시급도는 앱에서 쓰는 혼잡도 표기(혼잡 · 보통 · 여유)를 그대로 빌려 썼습니다.

| 시급도 | 건수 | 미루면 |
| --- | --- | --- |
| 혼잡 · 지금 | 3 | 코드 충돌과 중복 작업 발생 |
| 보통 · 이번 주 | 3 | 프런트엔드 다음 작업이 막힘 |
| 여유 · 확인만 | 4 | 없음 (기본값으로 진행) |

## 혼잡 · 지금 결정

셋 다 다른 팀원과 같은 파일을 건드리는 문제라, 합의가 늦어질수록 버리는 코드가 생깁니다.

### 1. 장소 상세 화면은 누가 소유하나

추천 카드를 누를 곳이 필요해서 `lib/src/screens/place_detail_screen.dart`를 만들었습니다.
장소명·주소·거리·혼잡도·분류·실내외·날씨를 모두 표기하고, 하단 버튼이 추천 탭 진입점 역할을 합니다.
그런데 원래 요구사항에서 상세 화면은 지도 탭 영역입니다. 지도 담당자가 같은 화면을 만들고 있다면
둘 중 하나는 버려야 합니다.

- **제안**: 지금 만든 상세 화면을 공용으로 쓰고, 지도 탭은 마커 → 상세 연결만 담당한다.
- 결정 주체: 지도 탭 담당 + 추천/저장 담당
- 막히는 것: 양쪽 상세 화면 작업

### 2. `Place` 모델과 목 데이터는 누가 관리하나

추천 계산에 필요해서 `Place`에 주소·위경도·`indoor_outdoor`·혼잡도 점수(0~100)·태그를 추가하고,
목 데이터를 3곳에서 13곳으로 늘렸습니다. 필드 구성은 백엔드 `Place` 모델에 맞췄습니다.
지도 탭도 같은 파일을 쓰기 때문에 동시에 고치면 충돌이 납니다.

- **제안**: 모델과 목 데이터는 추천/저장 담당이 관리하고, 필드가 더 필요하면 요청한다.
  실제 API 연동 레이어도 한 사람이 전담한다.
- 결정 주체: 프런트엔드 전원
- 막히는 것: 지도·홈 탭의 데이터 사용

### 3. 상태관리 방식을 지금 확정할지

취향·저장 목록·지도에서 넘어온 추천 요청을 전역에서 공유해야 해서, 외부 패키지 없이
`ChangeNotifier` + `InheritedWidget`으로 `AppScope`를 직접 만들었습니다.
팀에서 provider나 riverpod을 쓰기로 하면 지금 갈아타야 합니다.
화면이 더 늘어난 뒤에는 전 화면을 고쳐야 합니다.

- **제안**: 현재 규모에서는 지금 방식을 유지한다. 단, provider에 익숙한 팀원이 있으면 지금 바꾼다.
- 결정 주체: 프런트엔드 전원
- 막히는 것: 앞으로 추가되는 모든 화면

## 보통 · 이번 주 안

### 4. 취향과 저장 목록을 껐다 켜도 유지할까

지금은 메모리에만 있어서 앱을 재시작하면 저장한 장소와 설정한 취향이 모두 사라집니다.
시연에서 바로 드러납니다.

| 선택지 | 내용 | 비용 |
| --- | --- | --- |
| **A (제안)** | `shared_preferences`로 로컬 저장 | 반나절, 로그인 불필요 |
| B | 로그인 + 서버 저장 | 백엔드 사용자 API 일정에 의존 |
| C | 그대로 둔다 | 시연 때마다 다시 저장해야 함 |

- 결정 주체: 추천/저장 담당 + 백엔드 사용자 영역 담당

### 5. 취향 설문 항목 확정

사용자 의견을 받아 구성하기로 했는데, 지금 넣어 둔 항목은 다섯 개입니다.

- 혼잡도 선호 (한적한 곳 ↔ 활기찬 곳)
- 실내 / 실외
- 관심 카테고리
- 이동 가능 거리
- 날씨 반영 여부

추가 후보: 동행(혼자·연인·가족), 방문 시간대, 예산, 주차·대중교통 접근성.

설문을 실제로 돌릴 거라면 이번 주에 문항을 확정해야 결과를 반영할 시간이 남습니다.
돌리지 않는다면 현재 다섯 개로 확정합니다.

- 결정 주체: 팀 전체
- 막히는 것: 취향 설정 화면과 추천 가중치

### 6. 추천 점수를 앱에서 계산할지, 서버에서 계산할지

`DECISIONS.md`에서 추천 점수 API는 1차 구현 범위에서 빠져 있어 지금은 앱에서 계산합니다.
화면은 `Recommendation`(장소 + 점수 + 이유)만 보기 때문에 나중에 서버 점수로 바꾸기는 쉽습니다.

- **제안**: 발표까지는 앱 계산을 유지한다. 데이터 양이 적어 충분하고,
  백엔드는 장소·혼잡도 수집에 집중하는 편이 낫다.
- 결정 주체: 백엔드 추천 담당 + 추천/저장 담당
- 되돌리는 비용: 낮음

## 여유 · 확인만 해주면 되는 것

진행을 막지 않으려고 임의로 정해 둔 값입니다. 이견이 있는 줄만 알려주세요.

| 항목 | 지금 값 | 확인이 필요한 이유 |
| --- | --- | --- |
| 혼잡도 3단계 경계 | 0–33 여유 / 34–66 보통 / 67+ 혼잡 | 백엔드 `CrowdData` 기준과 같은 값이어야 함 |
| 장소 대분류 | TourAPI 6종 (12·14·15·28·38·39) | `DECISIONS.md`에서 여행코스(25)·숙박(32)은 "추천 요구가 확정되면 재결정"으로 남아 있음 |
| 대안 추천 반경 | 3km 고정 | 사용자가 직접 조절하게 할지 |
| 추천 가중치 | 혼잡도 .32 / 카테고리 .22 / 거리 .18 / 실내외 .16 / 날씨 .12 | 혼잡도 앱인 만큼 혼잡도 비중을 더 키울지 |

4. 날씨 API와 현재 위치(`geolocator`)는 지도 탭 일정에 맞춰 연결
