# 원스토어 1.0.0 서버 적용 계획

작성일: 2026-09-21. 통합 기준: PR #19의 `a59ba94fcdba3f9f72cc0ffe41e9b4b1d3b58056`.
기존 PR의 nginx 로그 정책 수정과 앱 로고 변경을 유지하고, 백업의 관리자 수동 삭제를 추가한다.
이 문서는 deployd 읽기 전용 조회와 코드 검토 결과다. 테스트, 이미지 발행, 운영 설정 변경,
마이그레이션 실행, 백업 삭제는 수행하지 않았다.

## 현재 운영 상태

- 앱 `ilion`, 이미지 저장소 `ghcr.io/hurdoo/ilion`.
- 상태 `healthy`, `runtime.healthy=true`, HTTP 200.
- 현재 커밋 `d4a94fd4a75236be04adaae380dc85772a392dce`.
- 마지막 배포 성공 시각: 2026-09-21 12:16:36 KST. 배포 식별자는 운영 대시보드에서 확인한다.
- 현재 DB 승인 대상: `users.0007_favorite_actor_feedback_actor_recentplace_actor_and_more`.
- `DATA_WORKER_ENABLED=true`; 필수 secret 두 개와 선택 secret 네 개의 등록 상태 확인.
  `secretsReady=true`, 누락 이름 없음. 값은 조회하지 않았다.
- 현재 코드가 기동 시 전체 미적용 migration 검사를 수행하고 정상 기동했으므로
  `0007`까지 적용된 상태로 판단한다. DB의 `django_migrations`를 직접 조회한 결과는 아니다.

## 적용할 변경

| 항목 | 현재 | 적용 계획 |
|---|---|---|
| 이미지 | `d4a94fd` | 로그 기간 반영과 수동 백업 정리를 포함한 최종 검토 커밋 |
| DB 승인 대상 | `users.0007_…` | `users.0008_user_signup_consent` |
| 비밀값 이름·등록 | 준비됨 | 새 이름이나 값 등록 불필요 |
| 포트·볼륨·리소스·수집 설정 | 현재 설정 | PR 기준 변경 없음 |
| 처리방침 | 운영에는 PR 미적용 | 작성자가 최대 15일 보관을 반영했으므로 새 이미지 배포 후 공개 |
| 배포 전 DB 백업 | 자동 생성, 자동 삭제 없음 | 자동 생성 유지, 각 백업 생성 후 30일에 관리자 수동 삭제 |

PR 기준 계약을 `deployctl plan`으로 확인했다. 이 명령은 테스트·빌드·발행을 하지 않는다.
수동 백업 정리 변경을 기존 PR에 통합한 최종 커밋으로 배포 계획과 이미지를 다시 생성해야 한다.

## 순서

1. PR 작성자가 전달받은 nginx logrotate 설정(`daily`, `rotate 14`)을 최대 15일 보관으로
   반영했고, Gunicorn의 중복 접속 로그를 끄는 변경도 추가했다(`f7d3966`).
   이로써 새 배포부터 요청마다 Docker 로그에 접속 기록을 중복으로 남기지 않는다.
   이미 쌓인 Docker 로그는 별도다. deployd의 현재 조회 응답에는 로깅 드라이버·보관 설정·
   이전 로그 파일 잔존 여부가 없으므로, 재배포만으로 삭제됐다고 단정하지 않는다.
   운영 관리자가 재배포 후 이전 컨테이너 로그, 외부 전송·보관본의 잔존 여부를 확인하고
   남아 있다면 접속 기록 보관 기준과 맞게 정리한다. 이 작업에서 과거 로그는 삭제하지 않았다.
2. 수동 백업 정리 변경을 PR에 통합하고, 작성자가 운영 문서와 PR 설명의 자동 삭제 표현을 수정한다.
   공개 페이지의 백업 설명과 문서 버전은 이 변경에 포함했다.
3. 최종 코드 리뷰·팀 검증 기록의 대상 커밋을 확인한 뒤 커밋/병합한다.
   앱 서명·판매자 정보·실기기 확인은 팀 담당 범위이며 이번 작업에서 다시 수행하지 않았다.
   PR의 기존 검증 설명만으로 Linux 검증 완료를 확정하지 않는다.
4. 최종 커밋에서 이미지와 전체 배포 설정을 함께 준비한다. 바뀌는 공개 설정은
   `DJANGO_MIGRATION_TARGET=users.0008_user_signup_consent`다.
   별도 **설정** 적용 대신 새 이미지와 함께 **배포** 제출에 포함한다.
   `deployctl publish`는 프로젝트 검사를 실행하므로 이번의 테스트 미실행 범위에서는 호출하지 않았다.
5. 사용자 관리 화면에서 최종 커밋·digest·전체 설정과 DB 업데이트를 확인하고 배포한다.
   현재 상태라면 `0008` 한 건이 적용되는 복구 경로가 사용된다. 런타임은 먼저 SQLite 백업과
   무결성 확인을 수행한다. 예상 밖의 미적용 migration이 있으면 적용을 거부한다.
6. 배포 후 deployd의 해당 작업 성공, 최종 커밋/digest, health 200을 확인하고,
   `/terms`, `/privacy`가 공개되는지 확인한다. 건강 상태만으로 두 문서의 공개 여부를 대신 판단하지 않는다.
   새 앱 출시도 이 시점에 맞춘다. 구버전 앱은 새 필수 가입 동의 값을 보내지 않는다.

이미지 롤백은 DB나 업로드 파일을 복원하지 않는다. `0008`은 동의 기록 열을 추가하는 변경이지만,
이전 이미지와의 호환성을 실행 검증한 것은 아니다. 문제 발생 시 배포 이력·현재 health·백업을
확인한 후 이미지 복구와 DB 복원이 필요한 경우를 구분한다. DB를 임의로 역마이그레이션하지 않는다.

## 관리자 수동 백업 삭제

사용자 확정 정책은 **각 백업 생성 후 30일에 관리자 수동 삭제**다. 30일마다 몰아서 삭제하는 방식이 아니다.
앱 기동과 수집 워커는 백업을 삭제하지 않는다. 탈퇴 회원과 후기 사진의 기존 파기 절차는 유지한다.

관리자는 새 배포 백업을 만든 시점에 30일 후 삭제 기한을 기록하고, 기한에 대상 파일을 확인한다.
다음 명령은 운영 앱의 환경과 저장소가 연결된 관리자 실행 환경에서 사용하는 앱 내부 명령이다.
현재 deployd 조회 도구에는 원격 명령 실행·백업 삭제 기능이 없으며, 이 문서는 호스트/컨테이너명을
추정한 명령을 제공하거나 삭제 예약을 설치하지 않는다.

```sh
# 읽기 전용 목록: 생성 후 30일이 지난 파일명·크기·생성 시각(UTC)
python manage.py cleanup_migration_backups

# 목록에서 확인한 파일명 하나를 직접 지정한 경우에만 삭제
python manage.py cleanup_migration_backups --delete '목록에서-확인한-정확한-파일명'
```

- `--delete`를 반복해 선택할 수 있다. 경로·와일드카드·전체 삭제 옵션은 없다.
- 모든 선택 파일을 먼저 검증한다. 삭제 시점에도 30일 경과 여부를 재확인한다.
- 생성 시각은 기존 런타임이 파일명에 기록한 UTC 시각을 사용한다. 파일 복사나 수정 시각 변경으로
  보관 기한이 뒤로 밀리지 않는다.
- 정해진 형식의 일반 `.sqlite3`/`.sqlite3.partial` 파일만 대상이다.
  현재 DB·WAL/SHM·사진·다른 백업·심볼릭 링크·하위 폴더는 제외한다.
- 삭제는 되돌릴 수 없으며 실제 삭제한 파일명을 출력한다. 도중 오류가 나면 중단하므로
  출력과 재조회 결과로 남은 파일을 확인한다.
- 수동 방식은 관리자가 기한을 지켜야 성립한다. 이 변경은 알림이나 자동 실행을 설치하지 않는다.
  별도 서버 스냅샷·수동 복사본이 존재하면 별도 보관·삭제 정책도 확인해야 한다.

## 이번 변경의 확인 범위

- 기본 조회의 비파괴성, 명시한 파일만 삭제, 30일 경계, 잘못된 혼합 선택의 전체 거부,
  경로 이탈·심볼릭 링크 제외를 다루도록 테스트 코드를 변경했다. 사용자 요청에 따라 실행하지 않았다.
- 원격 PR, 운영 서버, 운영 DB, 운영 백업은 변경하지 않았다.
