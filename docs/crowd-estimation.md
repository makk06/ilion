# 전국 관광지 혼잡도 추정 운영 안내

기준: 2026-09-12, 모델 `heuristic-v1`, 프로파일 `profiles-v1`. Django·SQLite·Flutter를 유지한다. 계수는 초기 설계값이며 현장 정확도 검증 수치가 아니다.

## 데이터와 해석

- KTO `KorService2`: 장소 식별·좌표·분류·상세·행사 원장. `PlaceSource(source, external_id)`를 재사용한다.
- 서울 도시데이터: 공식 **121개** 영역의 체류 인구와 최근 30분 하차량. 인구 전용 API는 인구 부분 장애의 보조 경로다.
- 기상청: 실황과 시각별 예보를 구분하여 격자 단위 공유. 한국천문연구원: 당해·다음 해 공휴일.
- 공급자 문서·갱신·단위·이용 조건은 `places/data/crowd_providers.json`에 기록했다. 실제 키의 승인 한도는 `.env`로 별도 지정한다.
- 서울의 공개 `sample` 키는 요청 영역과 무관하게 POI009를 반환한다. 표본 확인은 계정의 121개 영역 권한 확인이 아니다.
- 공식 WGS84 경계 원본은 `places/data/seoul_crowd_geometry.json`에 보존한다. POI070의 자기 교차는 가져올 때 Shapely `make_valid`로 보정하고 `geometry_repaired`를 기록한다.

점수는 장소 또는 영역에서 상대적으로 얼마나 방문이 많은지에 대한 추정이다. **물리적 밀도·안전도·시설 내부 인원·관광객 수가 아니다.** `estimated_visitors`는 항상 null이다. 개발 샘플과 서울 대체 인구는 실시간 근거 및 역사 인구 표본에서 제외한다.

## 초기 실행

백엔드 디렉터리에서 실행한다. 운영 SQLite 파일은 OneDrive 밖의 서버 로컬 영속 경로를 사용한다. 기존 DB는 배포 전에 SQLite 백업을 만든다.

```powershell
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py import_crowd_geometry --resolve
python manage.py verify_crowd_providers
python manage.py collect_crowd_inputs --once
python manage.py refresh_crowd_estimates
```

`verify_crowd_providers`는 KTO 목록·행사·상세, 서울 정식키 두 영역, 기상청 세 상품, 공휴일을 소량 확인한다. 키 또는 **승인 일일 한도**가 없으면 `blocked`를 출력한다. 키·응답 원문·인증 URL은 출력하지 않는다. 실제 요청 시도마다 예산을 차감한다. 이 명령과 수집기는 같은 DB 예산을 사용한다.

`.env.example`를 참고하여 `TOUR_API_SERVICE_KEY`, `SEOUL_OPEN_API_KEY`, `KMA_SERVICE_KEY`, `HOLIDAY_SERVICE_KEY`와 각 `*_DAILY_LIMIT`을 설정한다. 한도 기본값 0은 수집 비활성화다. 무료 한도 초과 시 유료 서비스로 전환하지 않는다.

서울 정상 예산은 승인량의 80%이며 121개 전체 영역을 유지한다.
2026-09-12 계정 설정: 사용자 제공 서울시 키를 서버 `.env`에 저장했다. 사용자 안내 한도는 1일 최대 1,000건 및 1회 최대 1,000건이다. 현재 수집 예산은 보수적으로 `SEOUL_DAILY_LIMIT=1000`으로 설정한다. 1회 응답 건수 제한을 호출 횟수와 구분하며, 도시데이터는 한 요청에 한 영역을 조회한다. 정규 예산 800회/일과 재시도·보조 여유 200회/일을 적용하면 121개 전체 영역 수집 주기는 220분이다. 실제 인증 및 계정 권한 검증은 별도로 수행해야 한다.


```
주기(분) = 5 × ceil(max(5, 1440 × 영역수 / floor(일일한도 × 0.8)) / 5)
```

5분 주기의 기본량은 34,848회/일이다. 재시도까지 같은 한도에 포함된다. 기상 격자는 최대 100개, 일 56회/격자의 예산으로 제한한다. 시도별 등록 격자를 우선하고 최근 상세 조회가 있는 프로파일 순으로 나머지를 선정한다. 조회 수요는 장소별 마지막 시각만 저장하며 사용자 ID나 GPS 경로를 저장하지 않는다. 격자 밖 장소의 최신 날씨는 없는 값으로 표시한다.

## 스케줄러와 운영 상태

웹 프로세스에는 스케줄러가 없다. OS에서 매분 `python manage.py collect_crowd_inputs --once --max-seconds 45`를 호출한다. `ops/ilion-crowd.service`, `.timer`, `ops/collect-crowd.ps1`은 배포 템플릿이다. 환경별 경로를 설정한 뒤 OS에 등록한다. 개발 작업 중 실제 반복 작업을 자동 등록하지 않는다.

`CollectorState`의 다음 실행 시각·커서·최근 성공·실패 횟수·임대 잠금·KST 일별 호출량을 확인한다. 한 작업은 한 수집 프로세스가 수행한다. 임대는 만료 후 회복되며 원격 요청 중 DB 트랜잭션을 유지하지 않는다. SQLite 쓰기는 짧게 한다.

`python manage.py crowd_status`는 영역 등록 수·최근 관측 누락/만료·공급자 예산·실패 작업을 비밀정보 없이 출력한다. 이 상태의 최근 관측 시각은 개발 샘플을 포함할 수 있으므로 실제 데이터 여부는 API `is_demo`도 함께 확인한다.

- 서울: 예산에 따른 주기 안에 영역을 분산한다. 도시데이터 정상 응답에 인구 전용 API를 추가 호출하지 않는다.
- KTO: 변경 일별, 전체 대조 주별, 행사 6시간, 미보강 상세 소량 우선. 페이지 중단 시 커서를 유지하며 완료 전에 전체 성공 시각을 갱신하지 않는다. 마지막 완주 시작 시각을 다음 변경 조회의 watermark로 사용한다.
- 기상청: 실황 매시 12분, 초단기예보 47분 이후, 단기예보 02·05·08·11·14·17·20·23시 발표 15분 이후. 같은 발표 자료를 반복 수집하지 않는다.
- 공휴일: 가까운 달 일별, 나머지 주별. 저장 달력이 없으면 확정 평일로 표시하지 않는다.
- 최신 추정: 매핑 장소 및 최근 조회 장소를 100개씩 분할 갱신. 사전 계산 없는 곳은 API가 DB 입력을 일괄 읽어 계산한다.
- 기준선·예측 평가·보존 정리: 04:10 KST. 인구·교통 30일, 시간별 표본·기준선·평가 400일.

HTTP는 연결 3초/읽기 10초, GET 최대 3회, 일시 오류만 재시도한다. 8MiB 응답 제한, XML DTD/entity 거부, 영역·좌표·인구 범위·시각 검증을 적용한다. 긴 Retry-After는 다음 실행으로 넘긴다. 연속 5회 실패하면 공급자를 15분 쉬게 한다. API 장애로 마지막 정상 데이터나 종료 미확인 행사를 삭제하지 않는다.

## 계산과 신뢰도

순수 계산 모듈은 `crowd_estimator`, `crowd_confidence`, `crowd_forecast`다. 외부 API를 호출하지 않는다. 원천 관측만 시간별 median 표본으로 집계한다. 5분 관측 12건은 독립 날짜 12개가 아니다.

최근 84일 중 동일 요일·시간 4개 날짜 이상이어야 조건부 기준선을 쓴다. 전체 시간 분포는 28개 날짜와 기대 시간 버킷 70% 이상이 필요하다. percentile은 시간별 분포가 아닌 영역 전체 분포의 mid-rank CDF를 쓴다. 동일값 분포는 50점이다. 경험 분포가 없을 때만 공급자 4단계 임시 anchor를 쓴다. 그 외 전국 장소는 유형·시간·휴일·계절 prior다.

```
uP = 0.8qP, uT = 0.2qT
delta = (uP × (PopulationScore-B) + uT × transitDelta) / (uP+uT)
a = min(0.9, 0.85qP+0.30qT)
Context = clip(12qE(E-Ebaseline) + 10qW(W-Wbaseline), -20, 20)
Score = round(clip(B + a × EWMA(delta) + (1-a) × Context, 0, 100))
```

분모 0이면 delta=0. 새로운 원천 관측에만 반감기 10분 EWMA를 적용하고 30분 단절 시 재설정한다. 지도 매핑·프로파일·기준선 버전이 바뀌면 상태를 섞지 않는다. 교통은 동일 집계창·수단의 과거 하차량과 비교하고 수단별 변화를 평균한다. 버스·지하철 사람 수를 더하지 않는다. 수집 시각밖에 없는 교통 품질은 0.6 이하이다.

행사는 2km 이내 거리 감쇠, 날짜만 확인되면 시간 가중치 0.35, 규모 미확인은 0.5이다. 수동 규모에는 근거와 유효기간이 필요하다. 습도는 저장하되 점수 계수는 0이다. 실내외 추론 시 날씨 효과를 한 번만 0.5배 적용한다.

신뢰도는 근거 품질 지수다. A/B/C 상한은 0.90/0.65/0.35, 넓은 영역 proxy 0.75, bootstrap 0.55, 시간 가정뿐이면 0.20 이하이다. 신선도 TTL은 인구 60분, 교통 30분, 날씨 4시간, 행사 72시간이다.

검증된 운영시간만 `opening_schedule`에 넣는다. 예:

```json
{"verified":true,"evidence":"운영자 확인 2026-09-12","valid_until":"2026-12-31","weekdays":{"0":[["09:00","18:00"]],"1":[]}}
```

빠진 요일은 미확인, 빈 배열은 확인된 휴무다. 야간 영업은 자정을 기준으로 검토해 나눈다. 자유문장 운영정보를 자동 확정하지 않는다. 폐장과 혼잡도는 별도 표시하며 폐장을 한산함 추천 근거로 쓰지 않는다.

## API와 앱 전환

`GET /api/places/{id}/crowd`는 현재·1/2/3시간 점수, 근거 품질, 입력 시점, 원천 범위, 설명 요인, 출처, 버전을 반환한다. 기존 `latest_crowd`의 4단계 계약과 필터는 유지한다. 목록·근처의 `crowd_estimate`는 요약, 상세에는 전체 설명을 제공한다. `estimate_level`은 페이지 나누기 전에 적용하며 `crowd_level`과 함께 보내면 400이다. 미등록·비활성 장소 404, 필수 메타데이터 오류는 200 unavailable, DB 장애는 503이다.

| 점수 | 코드 | 표시 |
|---|---|---|
| 0–20 | VERY_LOW | 매우 여유 |
| 21–40 | LOW | 여유 |
| 41–65 | NORMAL | 보통 |
| 66–85 | HIGH | 혼잡 |
| 86–100 | VERY_HIGH | 매우 혼잡 |

Flutter의 `CrowdEstimate`와 기존 `CrowdLevel`은 별개다. 공통 모델·배지가 카드·지도·상세·저장·추천에 같은 라벨을 제공한다. 저신뢰 값은 “예상 · 낮은 신뢰도”, 오래된 값과 개발 샘플은 별도 표시한다. 혼잡 선호 적합도는 `0.5 + confidence × (rawFit-0.5)`로 중립에 가깝게 만든다. 미제공·개발샘플·폐장·오래된 값에는 혼잡 가점을 주지 않는다.

`CROWD_ESTIMATION_ENABLED=false`로 기존 관측 응답으로 되돌릴 수 있다. DB를 되돌리거나 관측·매핑을 삭제할 필요가 없다. 새 앱도 새 필드가 없으면 기존 관측을 표시한다.

## 예측 평가와 출시 확인

`ForecastEvaluation`은 시간당 영역 대표 표본의 예측과 당시 경험 분포를 보존한다. 이후의 실제 인구를 그 분포로 변환하여 모델·baseline-only·persistence MAE를 비교한다. 공급자 예측과 모델 자신의 결과는 정답으로 쓰지 않는다. 최소 100개 및 7개 날짜의 평가가 있고 모델 MAE가 baseline 대비 10% 초과 악화되면 해당 horizon의 잔차·trend를 끄고 baseline+환경 결과로 전환한다. `system/evaluation`의 `disabled_horizons`는 운영 검토 전까지 유지한다. 실제 현장 정확도나 POI 내부 정확도를 검증한 것으로 해석하지 않는다.

```powershell
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
python manage.py evaluate_crowd_forecasts
# 저장소 루트, 반드시 새 폐기 가능한 DB 경로 사용
python scripts/benchmark_crowd.py --database .integration-artifacts/new-benchmark.sqlite3
# 프런트엔드 디렉터리
flutter analyze --no-pub
flutter test --no-pub
flutter build web --no-pub
```

최초 로컬 성능 측정(10만 POI·121영역, 30회, warm Django test client): 상세 p95 54.11ms, 일반 목록 p95 368.35ms. 이는 네트워크·동시 수집 쓰기·전국 혼잡 필터 전체 스캔을 포함하지 않는다. 운영 동시 부하와 승인 쿼터 내 완주, 실제 키 인증, 최소 28일 관측 축적, 현장 평가가 별도로 필요하다. SQLite가 계속 잠기거나 운영 목표를 넘으면 PostgreSQL 전환을 검토한다.

### TourAPI 계정 설정 (2026-09-12)

사용자 제공 키를 서버 `.env`에 저장했다. 안내된 승인 한도는 **기능별 일일 1,000회**다. 현재 수집기는 공급자 단위 예산을 사용하므로 `TOUR_API_DAILY_LIMIT=1000`으로 설정하여 모든 기능 합계 일일 1,000회 이내로 보수적으로 제한한다(정규 800회, 재시도 여유 200회). 이는 공급자의 기능별 한도를 전체 합계 한도로 해석한다는 뜻이 아니라 로컬 수집 제한이다. 전달된 URL 인코딩 키는 기존 클라이언트가 디코딩 후 요청 파라미터로 전달한다. 실제 인증 호출은 별도 검증이 필요하다.

### 기상청 계정 설정 (2026-09-12)
