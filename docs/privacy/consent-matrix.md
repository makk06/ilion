## 1. 분류 결과 개요

| 분류코드 | 행 수 | 비율 | 의미 | 동의 화면 |

| `NO-CONSENT` | **96** | 78.0% | 동의 불요 — 계약이행·법령·안전조치 근거, 또는 개인정보 아님 | 체크박스 없음. 고지로 처리 |

### 왜 `REQ-CONSENT`가 0건인가

반대검토에서 **양방향으로 공격한 뒤에도 유지**되었습니다.

- **과소 분류 방향** — `NO-CONSENT` 96행 전부에 "정말 동의 없이 되는가"를 재적용했습니다. 승격이 필요한 것은 `REQ-CONSENT`가 아니라 `OPT-CONSENT`였습니다(최근 본 장소 2행).
- **과잉 분류 방향** — `STOP-COLLECT` 12건에 "과잉 절단인가"를 공격했습니다. 뒤집힌 것이 없습니다.
- **구조적 이유** — 계약 이행 범위를 넘는 처리 네 갈래(위치·국외이전·개인화·마케팅)가 **모두 실제로 동작하는 대체 경로를 코드에 가지고 있어** 전부 선택으로 강등됩니다.

### 🔴 그러나 "0건"은 "지금 적법하다"는 뜻이 아닙니다

**123행 중 32행이 현행 상태로는 방어되지 않습니다.**

| 표기 | 행 수 | 의미 |
|------|------|------|
| (표기 없음) | 91 | 현행 판정이 그대로 유효 |
| ⚠ **조건 미충족** | **27** | 고지·확인·토글이 필요한데 구현되어 있지 않음 |
| 🔴 **현재 무동의 처리 중** | **3** | 별도 동의가 필요한데 동의 없이 처리 중 (위치 3행) |
| 🔴 **최우선 시정** | **1** | `PD-R-001` — 동의가 아니라 §29 즉시 시정 대상 |
| ⚠ **처리 여부 결정 필요** | **1** | `PD-B-011` (`last_login`) |

**조건이 충족되면 표기를 떼고 기재된 분류코드가 그대로 유효해집니다.**

### ⚠ 이 결론을 무너뜨리는 단 하나의 제품 결정

**"지역 직접 선택" UX(`region_picker.dart` / `region_filter.dart`)는 편의 기능이 아니라 법적 리스크 통제 수단입니다.**

위치가 선택 동의로 강등된 유일한 근거는, 위치에 동의하지 않은 이용자가 **지역을 직접 골라 동일한 장소 목록·동일한 혼잡도·동일한 지도를 볼 수 있다**는 사실입니다(코드로 검증 완료).

이 대체 경로를 제거하면 **위치가 그 즉시 `REQ-CONSENT`로 승격**되고, "위치에 동의하지 않으면 서비스를 쓸 수 없다"는 구조가 되어 **PIPA §16**(최소수집 외 항목 미동의를 이유로 한 서비스 제공 거부 금지)과 정면으로 충돌합니다.

> **다음 변경은 법적 리스크를 새로 만드는 제품 결정입니다. 변경 전에 이 문서를 다시 검토하십시오.**
> - `RegionPicker`·지역 필터 제거
> - "내 주변" 없이는 목록이 비게 만드는 변경
> - 위치 미동의 시 특정 화면 진입 차단

### 동의 화면은 4단계로 나뉩니다

```
① 회원가입 화면      : [필수] 이용약관 + 연령 확인 + 개인정보 고지 + [선택] 개인화
② 구글 로그인 버튼 탭 : [선택] 국외 이전 동의          ← 가입 화면이 아님
③ 위치 기능 첫 사용   : 위치기반서비스 약관 + [선택] 위치  ← 가입 화면이 아님
④ 작성·행위 시점     : 공개범위 고지 (동의 아님)
```

> **"전체 동의" 하나로 ①~③을 묶으면 §22 구분 동의 위반입니다.**

### 앞으로 하기 쉬운 실수

| 실수 | 왜 위법 소지인가 |
|------|----------------|
| 이메일·비밀번호·닉네임을 `[필수] 개인정보 수집·이용 동의`로 묶기 | §15①4로 동의 불요. 동의 남용이자 §22 취지 위반 |
| 위치를 개인정보 동의 묶음 안에 넣기 | 위치정보법 별도 동의 위반. 근거 법률·철회 방법이 다름 |
| 위치를 `[필수]`로 만들기 | §16 위반 소지. 대체 UX가 이미 있어 정당화 불가 |
| 마케팅을 다른 동의와 함께 받기 | 망법 §50 + PIPA §22 양쪽 위반 |
| "전체 동의" 하나로 전부 묶기 | §22 구분 동의 위반 |
| 선택 체크박스를 기본 선택 상태로 두기 | 유효한 동의로 보기 어려움 |
| 선택 미동의 시 "이용 제한"이라고 안내 | 실제로 제한이 없는데 불이익을 과장하는 것 자체가 문제 |

## 3. 필수 동의 항목 — 0건

**`REQ-CONSENT`로 분류된 항목이 하나도 없습니다.**

> **`[필수] 개인정보 수집·이용 동의` 체크박스를 만들지 마십시오.**
> 이메일·비밀번호·닉네임은 §15①4로 동의 불요이며, 이를 필수 동의로 포장하는 것은 동의 남용입니다.
> 이용자는 거부할 수 없는 항목에 "동의" 버튼을 누르게 되고, 이는 §22 구분 동의의 취지에 반합니다.

### 가입 화면에 남는 체크박스

| 체크박스 | 상태 |
|---------|------|
| `[필수] 서비스 이용약관 동의` | ✅ **확정.** 개인정보 동의가 아니라 **계약 청약**입니다 |
| `[필수] 만 14세 이상입니다` | ❌ **채택 불가.** 아래 참조 |

#### 🔴 `[결정 필요]` — 자기신고형 체크박스는 §22의2를 갈음하지 못합니다

`[필수] 만 14세 이상입니다` 체크박스 한 줄로는 §22의2가 요구하는 **"법정대리인의 동의"**를 갈음할 수 없습니다.

| 사실 | 내용 |
|------|------|
| 현재 수집 항목 | `SignupSerializer`는 email·password·nickname만 받습니다 |
| 연령 필드 | 생년월일·연령 필드가 **전 저장소에 존재하지 않습니다** |
| 위험도 | 관광·여행 앱은 미성년 이용 개연성이 실제로 높습니다 |
| 이중 의무 | 개인위치정보에는 **위치정보법 아동 특례가 추가로** 걸립니다 |

**결정해야 할 두 안**

| 안 | 내용 | 비용 |
|----|------|------|
| ① | 생년월일 입력 → **만 14세 미만 가입 차단** | 낮음. 단순하고 일반적 |
| ② | **법정대리인 동의 절차 구현** | 높음. 동의 확인 수단 필요 |

> **"아무것도 안 하기"는 선택지가 아닙니다.** 이 결정이 내려지기 전까지 가입 화면의 연령 확인 블록 문안은 확정할 수 없습니다.

### 미동의 시 동작 — 문안의 "거부 시 불이익" 문구가 됩니다

| id | 미동의 시 |
|----|----------|
| `PD-B-007(b)` | **추천 결과는 그대로 제공됩니다.** 내 취향값이 모델 개선·통계 집계에서 제외될 뿐이고 **화면상 차이는 없습니다** |

### ⚠ `PD-B-028(a)` / `PD-F-030(a)` — 왜 승격되었는가

## 6. 동의 없이 처리 가능한 항목 — 96행

### 6-1. 왜 동의가 불필요한가

| 근거 | 행 수 | 대표 항목 |
|------|------|----------|
| **PIPA §15①4 — 계약 체결·이행에 필요** | **72** | 이메일·비밀번호·닉네임·토큰·찜·여행 일정·문의·검색어·게시물 |
| **개인정보가 아님** | 13 | `PD-B-049`(평균 평점), `PD-B-050`(수요 신호), `PD-B-064`(혼잡도 관측값), `PD-F-042`(온보딩 완료 여부) |
| **PIPA §29·§31 — 법령상 의무·안전조치** | 10 | `PD-B-037`(관리자 작업 로그), `PD-B-054`(접속기록), `PD-B-012`(권한정보) |
| 조건부 (도입 시 계약 이행) | 1 | `PD-B-061`(제휴 리워드 실물 발급) |

**§15①4 항목의 핵심**: 이 정보 없이는 **계약 자체가 성립하지 않으므로 "거부"라는 개념이 성립하지 않습니다.** 동의를 받을 일이 아니라 고지할 일입니다.

**§29·§31 항목의 핵심**: 접속기록·관리자 로그는 동의를 받을 항목이 아니라 오히려 **보관·구현해야 하는** 항목입니다.

### 6-2. ⚠ 고지가 없으면 이 판정은 성립하지 않습니다 — 27행

`NO-CONSENT` 중 **27행은 "고지를 한다면"이라는 조건이 붙은 판정**이며, **그 고지가 현재 하나도 구현되어 있지 않습니다**(앱 전수 확인).

> **"구조상 공개"는 고지 의무의 면제가 아니라 동의를 고지로 갈음할 수 있다는 뜻입니다. 고지가 없으면 갈음 자체가 성립하지 않습니다.**

| 조건 유형 | 해당 행 수 | 대상 id | 현재 |
|----------|----------|--------|------|
| **공개범위 고지** (작성 화면·입력란) | 21행 | `PD-B-003`·017·018·019·021·024·025·026·045·046·048 / `PD-F-011`·015·016·017·018·021·022·023·024·027 | **0건** |
| **행위 시점 고지** (버튼 근처) | 6행 | `PD-B-022`·027·047 / `PD-F-025`·028·046 | **0건** |

#### 필요한 고지 문구 6종 (동의 아님 — 부속 조치)

| 대상 | 고지 문구 | 위치 |
|------|----------|------|
| 후기 게시 | "작성한 후기와 사진은 로그인하지 않은 사람에게도 공개됩니다." | 작성 화면 상단 |
| 동행 게시 | "이 글은 로그인하지 않은 사람에게도 공개됩니다. **날짜·시각·장소**가 함께 공개됩니다." | 게시 직전 확인 화면 |
| 닉네임 입력 | "닉네임은 후기·동행 글에서 다른 이용자(비로그인 포함)에게 보입니다." | 입력란 바로 아래 |
| 좋아요 | "좋아요를 누르면 작성자에게 내 닉네임이 전달됩니다." | 버튼 근처 |
| 동행 신청 | "신청하면 모집자에게 내 닉네임이 전달됩니다." | 버튼 근처 |
| 길찾기 | "외부 서비스(카카오맵)로 이동합니다." | 버튼 근처 |

> **좋아요·동행 신청은 현재 앱 UI가 집계만 보여 익명을 시사하지만, 서버는 작성자에게 닉네임을 알림으로 전달합니다.** 이 오인을 버튼 근처 고지로 해소해야 합니다.

전체 문안은 [동의 화면 문안 — 문안 E](consent-copy.md)에 있습니다.

### 6-3. ⚠ 고지만으로는 부족한 것 — 동행 모집 노출 축소 4건

**고지는 작성자에게 알릴 뿐 제3자의 수집을 전혀 막지 못합니다.**

코드로 확인된 결합 위험과 조치 4건은 [보안 결함 상세 §4](security-findings.md)에 있습니다. 요지는 **"닉네임 X가 10월 3일 서귀포시 어디에 몇 시에 나오는가"를 앱 UI만으로 조회할 수 있다**는 것이며, **4건 중 3건이 코드 1~2줄**입니다.

> **법적 분류는 이 조치들과 무관하게 `NO-CONSENT`(구조상 공개)로 유지합니다.** 다만 §3(최소 침해 방식 처리 원칙)상 "고지했으니 되었다"는 방어는 약하고, 비용이 낮다는 점이 비례성 판단에서 불리합니다.

### 6-4. 자유서술 필드의 민감정보 유입 — 동의로 풀지 않습니다

대상: `Feedback.memo`(무제한), `Review.text`(공개), `Companion.text`(공개), `Inquiry.text`(비공개·운영자 열람).

> **이 경로들을 민감정보 별도 동의(§23) 항목으로 만들면 안 됩니다.**
> 민감정보 동의를 받는다는 것은 사업자가 민감정보를 **수집 항목으로 선언**한다는 뜻이고, 그 순간 §23의 처리자 의무를 전부 떠안게 됩니다.
> 필요한 것은 **유입을 줄이고, 유입분을 처리 항목으로 삼지 않는 구조**입니다.

|------|------|---------|
| 입력란 하단 고정 안내 — "건강·신념 등 민감한 개인정보는 입력하지 말아 주세요" | 4개 필드 전부 | 1 |

### 판정이 까다로웠던 항목 4건

**`PD-B-006` 구글 프로필 이미지 URL** — 앱 전수 grep 0건으로 "쓰이지 않음"이 확인되었으나, `ProfileSerializer.fields`(`activity_serializers.py:13`)에 들어 있어 **`/me` 응답으로 클라이언트까지 전송되고 있습니다.** 모델 필드뿐 아니라 **응답 필드에서도 제거**해야 합니다.

**`PD-B-034` 피드백 자유 메모** — "500자 제한 한 줄이면 되는데 수집 중단은 과잉"이라는 반론이 제기되었다가 **철회**되었습니다. 앱 코드에 `POST /api/feedback` 호출이 **0건**이기 때문입니다. 이 필드는 민감정보 유입 이전에 **UI도 클라이언트도 없는 순수 쓰기 가능 필드**이며, 그것이 1차 근거입니다.
**재도입 조건 3가지**: ①500자 길이 제한 ②입력란 하단 민감정보 안내 고정 ③유입 탐지·삭제 절차와 담당자 지정. 충족 시 `OPT-CONSENT`로 복귀합니다.

**`PD-F-001` 정밀 위치 권한** — 조치 순서가 교체되었습니다. "`ACCESS_FINE_LOCATION` 선언 제거"는 **Android 매니페스트 항목이라 iOS에 아무 효과가 없습니다**(iOS는 정밀도 축소 키가 없어 기본 전체 정확도로 동작). 양 플랫폼 공통의 실효 조치는 하나뿐입니다 — **`place_location.dart:19-20`의 `LocationSettings`에 `accuracy` 명시**(현재 미지정 → `best` 적용).
**반대 논거 병기**: 지도 마커 정밀도 저하는 제품 결정이며, 정밀도를 유지하려면 그 필요성을 위치 동의 문안에 명시해야 합니다.

**`PD-B-020` / `PD-F-020` EXIF** — 조치 우선순위가 뒤집혔습니다. 클라이언트 측 제거를 주 조치로 삼을 수 없습니다: ①`pickImage(maxWidth:1600)`는 **원본이 1600px를 초과할 때만** 리사이즈하므로 이미 축소된 사진·스크린샷은 원본 바이트가 그대로 올라갑니다 ②클라이언트 측 제거는 **변조된 클라이언트가 우회**할 수 있습니다.
→ **서버측 재인코딩이 주 조치, 프론트 제거는 보조.** 실기기 EXIF 검증 결과와 **무관하게** 서버측 조치는 필수입니다.

### 8-2. ⚠ `PD-B-011` — 처리방침에 쓰기 전에 결정해야 합니다

JWT 로그인 경로(`users/views.py:82-95`)가 `django.contrib.auth.login()`을 호출하지 않아 **`last_login`은 API 이용자에게 영원히 NULL**입니다.

이 상태로 처리방침에 옮기면 **"수집한다고 고지했으나 실제로는 수집하지 않는 항목"**이 되어 §30 일치 요건을 위반합니다.

| 안 | 내용 |
|----|------|
| ① | 휴면 정책을 실제로 쓸 것이면 **로그인 시 갱신 코드 추가** |
| ② | 쓰지 않을 것이면 **처리방침 기재 대상에서 제외** |

> **결정 전에는 처리방침에 넣지 마십시오.**

### 8-3. 동의 이전에 존재해야 하는 것이 없습니다

| # | 격차 | 결과 |
|---|------|------|
| 0 | 🔴 토큰 서명키가 저장소에 평문 커밋 (`PD-R-001`) | **토큰을 위조할 수 있는 상태에서 받은 동의는 의미가 없습니다** |
| 1 | **동의 상태를 저장할 모델 자체가 없습니다** | `User`에 동의 관련 필드가 하나도 없어 **받아도 저장할 곳이 없습니다** |
| 2 | **동의 UI가 앱 어디에도 없습니다** | 온보딩은 `시작하기` 버튼 하나뿐 |
| 3 | **보유기간이 하나도 정해져 있지 않습니다** | §15②3을 충족할 수 없어 **문안과 처리방침을 쓸 수조차 없습니다** |
| 4 | **파기 로직이 전무합니다** | 자동 삭제는 혼잡도 원본(30일/400일)뿐인데 **그것은 개인정보가 아닙니다** |
| 5 | **회원 탈퇴 기능이 없습니다** | `Status.WITHDRAWN` 값만 정의. §36·§37 권리 행사 경로 부존재 |
| 6 | **연령 확인이 없습니다** | §22의2 대응 부재 |
| 7 | **처리방침·이용약관·위치기반서비스 이용약관 문서가 없습니다** | §30 미이행. 위치 동의는 "이용약관에 명시한 후" 받아야 하므로 **문서 없이는 동의 자체가 불가** |

> ### 🔴 순서를 바꿀 수 없는 의존 관계
> **회원 탈퇴 기능과 항목별 보유기간·파기 정책이 정해지기 전에는 개인정보 처리방침을 쓸 수조차 없습니다.**
>
> §15②3(보유·이용 기간 고지)과 §30(처리방침 기재사항)은 둘 다 "얼마나 보관하고 언제 어떻게 파기하는가"를 요구합니다. 이것이 정해지지 않은 상태에서 처리방침을 작성하면 **그 문서 자체가 §30 위반물**이 됩니다.
>
> **순서**: 보유기간 확정 + 탈퇴 시 항목별 처리(삭제/익명화/보존) 결정 → 파기 로직 구현 → 처리방침 작성 → 공개
>
> 특히 `PD-B-023`(포인트 원장)은 **`PointEntry.place`가 `PROTECT`라 보존/파기 결정 없이는 탈퇴 로직 자체를 짤 수 없습니다.**
